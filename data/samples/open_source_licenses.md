# 常见开源许可证简介

## 什么是开源许可证

开源许可证是版权所有者授予他人使用、修改和分发软件的法律文本。按照著作权法，没有附带许可证的代码默认“保留所有权利”，别人即使能在网上看到源码，也无权合法地复制、修改或再发布。因此，一个项目只有附带了开源许可证，才算真正意义上的开源软件。

开放源代码促进会（Open Source Initiative，OSI）维护着一份经过审核的开源许可证列表，并给出了“开源定义”：许可证必须允许自由再分发、提供源代码、允许修改和派生作品，并且不得歧视任何个人、群体或使用领域。自由软件基金会（FSF）则从“自由软件”的角度提出了四项基本自由：运行软件的自由、研究和修改软件的自由、再分发副本的自由，以及分发修改后版本的自由。

按照对派生作品的要求，开源许可证大致可以分为两类：宽松型许可证和著佐权（Copyleft）许可证。

## 宽松型许可证

宽松型许可证（Permissive License）对使用者的限制很少，允许把代码用于闭源的商业软件，通常只要求保留原作者的版权声明。

### MIT 许可证

MIT 许可证源自麻省理工学院，是最简短、最流行的开源许可证之一。它允许任何人免费使用、复制、修改、合并、发布、分发、再许可和销售软件副本，唯一的条件是在软件的所有副本或重要部分中保留版权声明和许可声明。软件按“原样”提供，作者不承担任何担保责任。React、jQuery、Node.js、Ruby on Rails 和 LangChain 等项目都采用 MIT 许可证。

### BSD 许可证

BSD 许可证源自加州大学伯克利分校，常见的有二条款（BSD 2-Clause）和三条款（BSD 3-Clause）两个版本。BSD 3-Clause 与 MIT 很相似，额外规定：未经书面许可，不得使用原作者或贡献者的名字为衍生产品背书或做推广。Django 和 Flask 采用 BSD 3-Clause 许可证。

### Apache License 2.0

Apache License 2.0 由 Apache 软件基金会发布。它同样是宽松型许可证，但条款更完善：

- 明确的专利授权：每位贡献者都授予使用者使用其相关专利的许可；如果使用者就该软件发起专利诉讼，其获得的专利许可会自动终止；
- 修改说明：修改过的文件需要附上明显的修改声明；
- NOTICE 文件：如果原项目包含 NOTICE 文件，再分发时需要保留其中的声明；
- 不授予商标权：不能使用原项目的商标和名称做宣传。

由于专利条款对企业更友好，Kubernetes、TensorFlow、Android 开源项目（AOSP）的大部分代码以及 Streamlit 等项目都选择了 Apache 2.0。

## 著佐权许可证

著佐权（Copyleft）许可证要求：基于该软件修改或派生出的作品在分发时，必须继续使用相同（或兼容）的许可证并公开源代码，从而保证软件的自由能够传递下去。因为这种特性，它也常被通俗地称为“传染性”许可证。

### GPL

GNU 通用公共许可证（GNU General Public License，GPL）由自由软件基金会发布，是最具代表性的强著佐权许可证。如果你分发了 GPL 软件或其派生作品，就必须以 GPL 提供完整的对应源代码。GPL 并不禁止商业使用，也允许出售软件；仅在个人或公司内部使用、不对外分发时，也不会触发公开源代码的义务。

GPL 目前常用的是 GPLv2 和 GPLv3。GPLv3 于 2007 年发布，相比 GPLv2 增加了明确的专利授权条款，以及防止“Tivo 化”（用硬件限制阻止用户运行修改后的软件）的条款。Linux 内核采用 GPLv2，GCC 和 Bash 等 GNU 工具采用 GPLv3。

### LGPL

GNU 宽通用公共许可证（LGPL）是一种弱著佐权许可证，主要用于函数库。在允许用户替换该库等条件下，闭源程序通常可以通过动态链接的方式使用 LGPL 库，而无需公开自身代码；但如果修改了 LGPL 库本身，修改后的库仍需以 LGPL 开源。GNU C 库（glibc）采用 LGPL。

### AGPL

GNU Affero 通用公共许可证（AGPL）在 GPLv3 的基础上增加了网络服务条款：如果你修改了 AGPL 软件并通过网络向用户提供服务，即使没有分发软件本身，也必须向这些用户提供修改后的源代码。它堵住了 GPL 在 SaaS（软件即服务）场景下的漏洞。Grafana 目前采用 AGPLv3，MongoDB 在 2018 年改用 SSPL 之前也采用 AGPL。

### MPL 2.0

Mozilla 公共许可证 2.0（MPL 2.0）是以文件为单位的弱著佐权许可证：修改过的 MPL 文件必须开源，但同一个项目中的其他文件可以使用别的许可证，甚至闭源。Firefox 浏览器采用 MPL 2.0。

## 主流许可证对比

| 许可证 | 类型 | 能否集成到闭源软件中分发 | 修改后是否须开源 | 明确的专利授权 | 代表项目 |
| --- | --- | --- | --- | --- | --- |
| MIT | 宽松 | 可以 | 不需要 | 无 | React、LangChain |
| BSD 3-Clause | 宽松 | 可以 | 不需要 | 无 | Django、Flask |
| Apache 2.0 | 宽松 | 可以 | 不需要，但要注明修改 | 有 | Kubernetes、TensorFlow |
| MPL 2.0 | 弱著佐权 | 可以 | 修改过的文件须开源 | 有 | Firefox |
| LGPL | 弱著佐权 | 可以（动态链接） | 修改过的库须开源 | v3 有 | glibc |
| GPLv3 | 强著佐权 | 不可以 | 整个派生作品须开源 | 有 | GCC、Bash |
| AGPLv3 | 强著佐权 | 不可以 | 通过网络提供服务也须开源 | 有 | Grafana |

## 如何选择许可证

- 希望项目被尽可能广泛地使用（包括商业公司），选择 MIT 或 Apache 2.0；
- 项目涉及专利，或者希望得到更完善的法律保护，优先选择 Apache 2.0；
- 希望所有基于你代码的改进都回馈开源社区，选择 GPLv3；
- 开发的是函数库，既想让闭源软件也能使用，又想让对库本身的修改保持开源，选择 LGPL 或 MPL 2.0；
- 软件主要以网络服务的形式提供，并希望服务端的修改也开源，选择 AGPLv3。

也可以参考 GitHub 提供的 choosealicense.com 网站。在 GitHub 上新建仓库时可以直接选择许可证模板，生成的 LICENSE 文件放在仓库根目录即可。

## 许可证兼容性

把不同许可证的代码组合在一起时，需要注意许可证兼容性。宽松型许可证（MIT、BSD、Apache 2.0）的代码一般可以并入 GPL 项目，组合后的整体按 GPL 分发；反过来，不能把 GPL 代码放进 MIT 项目后再整体按 MIT 发布，更不能闭源分发。需要特别注意的是：Apache 2.0 与 GPLv3 兼容，但按照自由软件基金会的观点，它与 GPLv2 不兼容。
